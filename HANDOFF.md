# Pantry Pal — Project Handoff

Last updated: 2026-07-04. Repo: [github.com/travisbrant1-cyber/r1-pantry-pal](https://github.com/travisbrant1-cyber/r1-pantry-pal). Live: [travisbrant1-cyber.github.io/r1-pantry-pal](https://travisbrant1-cyber.github.io/r1-pantry-pal/). Install QR: `r1-creation-qr-codes/pantry-pal-qr.png` on the machine this was built on (not in this repo).

This is a **Rabbit R1 Creation** — a static HTML/CSS/JS app that runs full-screen on the R1 device. If you're picking this up fresh, also read the `r1-creation` skill (`~/.claude/skills/r1-creation/`) for the general R1 platform facts and deploy pipeline this project follows — this doc only covers what's specific to Pantry Pal.

**Also runs in any standard browser (phone or desktop), same codebase, same CSS.** No separate build/branch - see "Cross-platform support" below for how the one R1-only interaction gap (hold-to-cancel) and the fixed-size layout were bridged without changing the visual design at all.

## What this is

A home inventory tracker. Scan a barcode, it looks up the product and lets you log a quantity in a few seconds. Point of the whole exercise, from the original proposal: **"Scan once. Know what you have. Never buy it twice by accident."**

## Status: Phase 1 done, plus two Phase-2 items pulled forward

The original proposal (see "Original spec" below) defines four phases. What's actually built:

**Done:**
- Barcode scanning (tap-to-capture, not continuous — see "Why tap-to-capture" below). Reads the printed digit line via OCR, not the bars themselves — see "OCR-only scanning" below for why bar decoding was dropped entirely. If barcode OCR finds no valid code, falls back to reading the brand/product name text and pre-filling manual entry with it — see "Product-name OCR fallback" below.
- Real Open Food Facts API lookup, with local cache always overriding external lookup for a barcode already seen once
- Local inventory storage (`window.creationStorage.plain`, JSON blob, no account needed)
- Add / adjust-quantity / remove-entirely flows
- Manual entry (both as the "barcode not found" fallback and as its own direct Home menu item)
- Inventory browser + item detail view
- Fractional quantities (1/4, 1/2, 3/4) for bulk goods, via tap-to-toggle on any quantity field
- Vision AI attempt and Web Speech API voice entry as unknown-product recovery options (pulled forward from Phase 2 — see caveats below, these are real but weak)

**Not started** (still Phase 2–4 per the original roadmap, unchanged):
- Expiration tracking + notifications
- Shopping list, recipes, statistics, multi-location switching UI (the `location` field exists on every item and defaults to "Pantry", but there's no UI yet to create/switch locations)
- Household sync, shared inventories, cloud backup

## Architecture

Vanilla JS, no build step, no framework — one `index.html`, `css/styles.css`, `js/app.js`, plus a vendored OCR library at `js/vendor/tesseract/` (self-hosted rather than CDN-loaded, so scanning still works with no internet — see the SDK's offline-first principle; also see "OCR-only scanning" below for the offline-first exception this actually has in practice on first use). `js/vendor/zxing.min.js` (the bar-decode library) was removed entirely once bar decoding was dropped — see below.

**State machine**: a single `showView(name)` function toggles `.active` on ten view `<div>`s (home, scan, lookup, itemCard, recovery, status, manual, browse, detail, diag). All navigation is scroll/click/hold/tap driven — see the in-app hint text on each screen for the current control mapping, it's kept in sync with behavior.

**Storage**: one JSON blob under the key `pantry_pal_inventory`, an array of items shaped like:
```json
{
  "id": "041196910123",
  "barcode": "041196910123",
  "productName": "Campbell's Tomato Soup",
  "brand": "Campbell's",
  "quantity": 4,
  "location": "Pantry",
  "image": "...",
  "source": "OpenFoodFacts",
  "lastUpdated": "2026-07-04"
}
```
`id` is the barcode when known, or a generated `manual-<timestamp>` id for barcode-less items (manual entries, homemade things). `expiration` isn't populated yet (Phase 2).

## Key design decisions and why

**Tap-to-capture instead of continuous video scanning.** The first version ran ZXing continuously against the live video feed. On the real device, camera setup (permission grant + stream init) takes real time, and the decode loop was only ever started once, at the exact moment of navigating into the Scan screen — so if the camera wasn't ready yet at that instant (very likely on first open), scanning silently never started. The user saw a live camera preview and assumed it was scanning; it wasn't. Rather than just patch the race (which was fixed once, in commit `cb6f4f9`), the whole approach was replaced: PTT click or a tap now captures one still frame and runs a single decode against it — simpler, more predictable, and matches the already-working Color Picker capture pattern.
**As soon as the still is captured, the UI leaves the live camera view** and switches to the existing status screen ("Reading barcode…") rather than staying on the live feed while OCR runs for a few seconds. Staying on live video during that wait made it look like the device still needed to be held steady, when the frame was already locked in — this was reported as confusing on real hardware and fixed by reusing the same status-screen pattern already used for Vision AI/voice. Holding PTT during this "Reading barcode…" state cancels to the recovery menu, same as it already does for the other status states.

**Barcode lookup is cache-first, permanently.** Once a barcode has been identified by any method (API, Vision AI, voice, manual), it's saved locally and a future scan of the same barcode never touches the network or the LLM again — `findByBarcode()` runs before any lookup path. Verified live against a real product (Nutella, barcode `3017620422003`).

**Vision AI is real but weak — be honest about this with users.** There is no documented way to attach a captured photo to a `PluginMessageHandler` message. The "Try vision AI" recovery option genuinely sends a request, but it can only ask the LLM to guess a "common grocery product" with zero visual grounding — in practice this means either no response at all, or a generic guess unrelated to the actual photo. Any result routes through the same editable "verify" screen as manual entry, so nothing can silently save a wrong name — but don't expect this to actually work. It's there because it was explicitly requested as an experiment, not because it's expected to deliver value yet. If Rabbit ever documents real image support, this is the one function to revisit: `attemptVisionAI()` in `js/app.js`. **Confirmed weak on real hardware**: a real attempt on the Orbit gum box returned answers ranging from "motors to relays" - zero visual grounding, exactly as expected. Not worth further investment; the `r1-creation` skill's `sdk-facts.md` independently confirms there's no documented way to attach an image to this bridge at all.

**Product-name OCR fallback: reads text instead of a barcode as a last resort, but doesn't call out to a live search API.** Added after Vision AI's real-hardware failure confirmed it's a dead end, and after barcode OCR (even with all its accuracy fixes) still occasionally can't recover a valid checksummed code. Reuses the same Tesseract worker as barcode OCR, but temporarily clears the digit whitelist (`tessedit_char_whitelist: ''`) to read general text, restoring the digit whitelist afterward so barcode OCR on the next scan is unaffected. `extractProductNameQuery()` reuses `clusterWordsIntoRows()` (built for barcode-vs-nutrition-table disambiguation) and picks the first row containing real letters, trying largest-font rows first - a brand/product name is normally printed larger than fine print. A live text search against Open Food Facts was tried and abandoned: neither of their search endpoints sends CORS headers permitting a direct browser fetch from a backend-less static site (confirmed via an actual browser fetch failing, not just `curl`, which doesn't enforce CORS and misleadingly appeared to work in manual testing) - only their single-barcode lookup API supports cross-origin use. Instead of a live search, the OCR'd text just pre-fills the manual-entry form (`onProductNameGuess()` → `enterManual(true)`, same "Verify AI guess"-style pattern already used for Vision AI results) - no network call, no CORS problem, still saves typing versus a blank form, and keeps the same edit-before-save safety net as every other recovery path.
**Product-name OCR must never auto-navigate - it originally did, and it broke reaching the recovery menu.** First version ran product-name OCR automatically the instant barcode OCR failed, and jumped straight to "Verify OCR guess" the moment it found *any* text with a couple of letters in it - including garbled nonsense misread from elsewhere in the frame. Real-hardware testing on the gum box showed exactly that: the app displayed "random letters" and the user could never actually reach the recovery menu (so the just-added "Enter barcode" option was unreachable whenever a bogus guess happened to match, which was often). Fixed by decoupling entirely: `identifyFromCanvas()` now only ever does barcode OCR - on failure it goes straight to the recovery menu, full stop. `tryBackgroundNameGuess()` kicks off product-name OCR silently once the recovery menu is already showing (fire-and-forget into `pendingNameGuess`, no UI feedback, cannot navigate anywhere on its own) and it only ever gets used if the user explicitly picks "Manual entry" afterward - `runRecoveryAction()`'s manual branch checks `pendingNameGuess` and pre-fills if it's ready by then, otherwise manual entry is just blank like always. Every recovery option (including "Enter barcode") is now always immediately reachable, regardless of what the background name-guess does or doesn't find. Verified in preview: an image with product-name text but no valid barcode now lands directly on the recovery menu with "Enter barcode" present, and picking "Manual entry" afterward correctly picks up the background guess once it's ready.

**Manual barcode entry/correction, pre-filled with OCR's raw (unvalidated) digit guess.** Added when the gum box still didn't resolve even with the product-name fallback (no product name text was legible either) - the user specifically asked for a way to fix a wrong OCR digit by hand rather than retype a whole UPC on the R1's full QWERTY keyboard. New "Enter barcode" option in the recovery menu (`enterBarcodeEntry()`, `RECOVERY_ACTIONS`) opens a dedicated `barcodeView`. Pre-filled via `lastOcrDigitGuess`, set in `attemptOcrFallback()` from `bestDigitGuessFromWords()` - the same top-priority (largest-font) row `clusterWordsIntoRows()` already identifies as the likely barcode line, but taken as raw digits regardless of whether the checksum passed, specifically so a close-but-wrong OCR read gives the user a real head start instead of a blank field. Saving (`saveBarcodeEntry()`) strips non-digits and feeds the result straight into the same `onBarcodeReady()` pipeline as a successful scan (cache check, then Open Food Facts lookup) - no checksum re-validation, since the user directly confirming the digits is a stronger signal of correctness than OCR's own guess.
**Uses a custom on-screen keypad, not `inputmode="numeric"` - real-device testing showed the R1's native keyboard doesn't honor it.** First version used `<input type="text" inputmode="numeric" pattern="[0-9]*">`, expecting a 10-key pad instead of the full keyboard (`type="number"` was deliberately avoided since it silently strips leading zeros, which real UPC/EAN codes commonly have) - on the actual device, the numeric keypad never appeared at all, most likely because the R1's own minimal on-screen keyboard just doesn't honor standard keyboard-hint attributes. Rather than keep guessing at HTML input hints the platform might not support, `barcodeInput` is now `readonly` and a custom 12-button grid (`.keypad`/`.key` in `index.html`/`css/styles.css`) supplies every digit directly (0-9, backspace, a checkmark "OK" that submits) - this works identically regardless of what the platform's native keyboard does or doesn't support, and matches the tap-driven interaction already used elsewhere (e.g. tap-to-capture). One real CSS bug caught along the way: `.key` buttons inherited the base `button { padding: 9px }` rule, which fought the CSS grid's `repeat(4, 1fr)` row sizing and pushed the view ~21px past the frame (caught via the `scrollHeight`/`clientHeight` check, not a screenshot) - fixed with an explicit `padding: 0` override on `.key`. Verified in preview end-to-end: tapping digits builds the display value correctly, backspace removes the last digit, and tapping OK resolves to the real product (Orbit Spearmint Gum) with its photo.

**Voice entry works but breaks "offline-first."** Uses the standard Web Speech API, which needs network access to a cloud STT provider — a deliberate, acknowledged exception to the spec's offline-first principle. Tested that it degrades gracefully (falls back to the recovery menu within ~1.5s on no-mic/no-speech rather than hanging) but real recognition accuracy on-device is unverified.

**OCR-only scanning: bar decoding was tried and dropped entirely, not kept as a first attempt.** Originally added as a fallback after ZXing bar decoding, tried first every scan. Real-hardware testing (including fixing resolution, capture, and the correct focus distance along the way) never got bar decoding to actually succeed even once — the working theory is the fixed-focus lens plus this camera's limits leave too few pixels-per-bar-module even at the correct distance, while the much larger printed digits underneath stayed readable. Given bars never worked in practice, ZXing was removed from the scan flow entirely (not just deprioritized) — `js/vendor/zxing.min.js` and its plumbing (`decodeFromCanvas()`, `getZXingHints()`, the burst-retry logic) were deleted rather than left dormant, since keeping unused, untested code around under a "might help someday" rationale isn't worth the complexity. Every scan (camera capture and the file-picker fallback) now goes straight to OCR via `attemptOcrFallback()`. If a different camera or a clip-on macro lens is ever tried and bar decoding becomes viable, this would need to be re-added from scratch (`git log` has the removed implementation if useful as a reference). Implementation: `js/vendor/tesseract/` (Tesseract.js + the `eng` fast-trained LSTM model, self-hosted to keep the offline-first principle — see below for why this is an exception in practice), lazy-loaded only on first use (~8MB), not part of initial page load. Any candidate digit string is required to pass the standard GTIN check-digit algorithm (`isValidGTIN()`) before being accepted as a real barcode — this is the safety net against a misread digit silently pulling up the wrong product, on top of the existing confirm-before-save screen.
**Extraction is scoped per row of words we cluster ourselves, not Tesseract's own "lines" and not the whole recognized text.** First real-hardware attempt concatenated tokens across `result.data.text` as one flattened blob - real packages usually have other printed numbers besides the barcode (lot/item codes), and merging tokens across unrelated print produced garbage like `828345035005273` instead of the real `662834503500`. Scoping to `result.data.lines` (Tesseract's own per-physical-line grouping) fixed that case, but a small package (a gum box) exposed a second, harder version of the same problem: its nutrition facts table sits close enough to the barcode that Tesseract's own line segmentation merged both into one recognized line, defeating the scoping again. `clusterWordsIntoRows()` now does this grouping itself from `result.data.words` (each with its own bbox), using a tighter vertical-overlap tolerance than Tesseract's, and tries the largest-average-font-height row first — a barcode's digit line is reliably printed larger than a dense nutrition table's numbers, so this doubles as a "most likely to be the barcode" heuristic, not just a disambiguator. `extractValidBarcodeFromOcrWords()` is the entry point; `extractValidBarcodeFromLineText()` still does the same-line token-concatenation-plus-checksum logic as before, just per computed row instead of per Tesseract line. Verified by reproducing the exact failure in a synthetic image (a dense cluster of small nutrition-fact-style numbers positioned just above a larger-font barcode digit line, matching the real gum box's layout) - correctly isolated and decoded the barcode, which the real Open Food Facts API confirmed is a real registered product (Orbit Spearmint Gum, `022000004840`).
**A misread guard bar can add one stray digit at either edge of a read - `tryValidGTIN()` tries trimming it off.** A barcode's tall guard bars (start/end/middle) look visually similar to the numeral "1" once OCR is restricted to a digit-only whitelist, and real-hardware testing on the same gum box showed exactly that: an otherwise-correct read with one extra leading digit. Rather than only accepting an exact-length checksum match, if the combined candidate string is exactly one character longer than a valid GTIN length (9, 13, or 14), it also tries trimming a single character off the start or the end and re-checking the checksum - deliberately only the edges, since that's the only place a guard bar could actually produce a stray digit, not the middle of the line. Verified by prepending a synthetic stray "1" to a known-good digit line and confirming it still recovers the correct barcode.
**Page segmentation mode was tried and reverted - measured regression, not a theoretical one.** After reports of inconsistent OCR even on a phone (not just the R1's known-bad camera), tried switching Tesseract's page segmentation mode to SPARSE_TEXT (`tessedit_pageseg_mode: '11'`) on the theory that scattered label text (barcode digits, brand name, nutrition facts, amid graphics/icons) suits it better than the default whole-page-of-body-text assumption. A direct A/B test against the same image proved the opposite: default PSM correctly read `0 220000 048400` (the true 13-digit code including its leading zero) while SPARSE_TEXT dropped the leading zero entirely, every time. Reverted to Tesseract's default PSM. Lesson for whoever touches this next: a plausible-sounding OCR tuning theory is worth *nothing* without a direct before/after test against the same image - don't ship one on reasoning alone.
**Preprocessing (grayscale + full-range contrast stretch) was added defensively, but couldn't be proven to fix a real failure in this environment.** `preprocessForOcr()` in `js/app.js` converts to grayscale and linearly stretches so the darkest/lightest pixels hit true black/white, applied to every OCR pass right after downscaling. Verified *safe* (doesn't break a case that already worked, including under a synthetic low-contrast + directional-shadow test and an even harsher uniform-contrast-compression test) but couldn't demonstrate it actually flips a real failure into a success - Tesseract's own internal adaptive binarization turned out to already handle uniform lighting/contrast issues fine on its own, and synthetic pixel-math degradation doesn't reproduce the kind of noise a real camera photo actually has (blur, glare, motion, JPEG artifacts). If OCR inconsistency persists after this, the next real step is getting an actual failing photo from a real device (like the gum box photo that led to the nutrition-table and guard-bar fixes) rather than more synthetic tuning - every OCR fix that's actually stuck in this project came from a concrete failing real-world example, not from reasoning about what "should" help.
**Crop to the viewfinder band before barcode OCR - a real failing iPhone photo (not just the R1) showed the actual problem: the barcode was only a small strip within a much larger photo of the whole package, so OCR read almost nothing (`"8 2"`), not garbled digits.** The on-screen viewfinder line (`.viewfinder-line`) had been purely decorative since it was added - an aiming hint with zero effect on what actually got captured or analyzed. `cropToViewfinderBand()` in `js/app.js` now crops the captured frame to a band around that line (80% width, ~34% height, centered) before the barcode-OCR pass specifically - not the stored item photo, and not the background product-name-guess pass, since brand/flavor text isn't necessarily printed where the user aimed the barcode. Replicates the *same* object-fit:cover crop math the visible `camPreview` element already does (using its own live `offsetWidth`/`offsetHeight`, not a hardcoded constant) so the analyzed region matches what was actually visible on screen, not the camera's full uncropped sensor output. Tried cropped-first with a full-frame fallback if that misses (`identifyFromCanvas(cropToViewfinderBand(c)).catch(() => identifyFromCanvas(c))`) rather than cropping unconditionally, since aiming won't always be perfect - this can only help a previously-failing capture, never break a previously-working one. Only wired into the live-camera path (`attemptCapture()`); the file-picker fallback has no on-screen viewfinder to crop to, so it still analyzes the whole picked photo. Not independently verified against a real degraded photo in this environment (synthetic test compositing a real barcode into a large blank canvas didn't reproduce a failure either way - it's the same limitation noted above, a rendered composite isn't real camera noise), but the underlying crop math was verified correct, and this is close to universal practice in real barcode-scanning apps for exactly this reason.
**The recovery-screen photo preview was both distorted and misleading - fixed to show what OCR actually analyzed.** A user screenshot exposed two separate bugs at once: `makeThumbnail()` forced every stored/displayed photo into a fixed 160x120 box by *stretching* rather than preserving aspect ratio (a real captured photo is rarely 4:3, so this visibly distorted every thumbnail app-wide, not just this screen) - now uses a "contain" fit (scaled, centered, letterboxed with the app's own `--bg-sunken` color) instead. Separately, the recovery screen's photo was always the full uncropped capture, never the actual region `cropToViewfinderBand()` fed to OCR - meaning a failure could never be visually diagnosed against what OCR really saw. `lastOcrAnalyzedCanvas` now tracks the literal post-crop, post-preprocess canvas from the most recent OCR attempt (reset per attempt in `identifyFromCanvas()`), and `renderRecoveryPhoto()` shows a thumbnail of *that* instead of the raw photo when one's available. Caught one more real bug while verifying this: `preprocessForOcr()`'s contrast stretch divides by the image's actual min/max range, which degenerates to dividing by ~0 (collapsing everything to solid black) on a perfectly flat/uniform test image - added a floor (`Math.max(hi - lo, 30)`) so a genuinely low-contrast real photo doesn't get destroyed the same way; a real photo will essentially never be perfectly flat, but the floor costs nothing and removes the pathological case entirely.
**That fix introduced its own visible bug - a second, uncontrolled crop stacking on top of the first one - caught from another user screenshot.** `makeThumbnail()` fits into a fixed 160x120 (4:3) box, but `recoveryPhoto`'s real CSS box is nothing like 4:3 - full card width, only 32px tall (~7:1). Feeding a 4:3-fitted thumbnail into a 7:1 `background-size: cover` box meant CSS did a *second* crop on top of an already-fitted image, and the two compounded unpredictably depending on the source's own aspect ratio - visibly wrong, dark bars in confusing places. `makeCoverFitThumbnail()` now does one direct "cover" fit straight into the element's own live-measured box size (`recoveryPhoto.offsetWidth`/`offsetHeight`) instead of going through the generic 160x120 thumbnail path at all - only one crop, matching what's actually about to be displayed. Verified by rendering a distinctive striped test pattern through a real OCR failure and confirming the generated image's height exactly matches the box's real height (no more mismatched double-fit) and the stripe pattern is visibly intact across the image rather than degenerately cropped.
**Live focus/framing indicator - colors the viewfinder line in real time, before capture.** After a user found there's a specific distance where scans reliably succeed but had to find it by trial and error (each attempt costs a several-second OCR round trip), added continuous feedback on the *live* video instead. `measureLiveFocusScore()` runs every 250ms while the scan screen is showing and the camera is live (started/stopped centrally from `showView()`, not scattered per-caller): downscales the current video frame, crops it through the *same* `cropToViewfinderBand()` used for real OCR, and scores it with `computeSharpnessScore()` - a simple gradient-magnitude/edge-energy metric (sum of absolute pixel-to-pixel differences, both directions, averaged per pixel). A small/blurry/poorly-framed barcode has much less fine detail than a sharp, well-filled one, so this doubles as a proxy for both focus *and* framing at once, which matches what actually varies as distance changes. Verified the metric itself behaves correctly on synthetic sharp vs. blurred vs. blank test patterns (scores of ~66, ~3, and 0 respectively - a clean, well-separated signal) - genuinely live-camera behavior (the color actually changing as a real phone moves) is unverified on real hardware.
**Deliberately relative, not an absolute calibrated threshold.** `viewfinderLine`'s color is driven by the *current* score as a fraction of the highest score seen so far this scan session (`bestFocusScoreSeen`, reset each time the scan screen is (re-)entered), interpolated red (0) to green (120) in HSL - not a hardcoded "score > X is good" cutoff, since there was no way to calibrate one without real hardware in hand, and lighting/camera quality vary a lot device to device. This makes it behave like a "hot/cold" game: green means "as good as it's gotten so far this attempt," not "guaranteed readable" - reasonable given the goal is guiding the user toward a better position, not certifying one. If real-device testing shows the feedback feels laggy, unresponsive, or miscalibrated (e.g. green triggers too easily, or the color never seems to change), the two knobs to revisit are `FOCUS_CHECK_MS` (currently 250) and whether `bestFocusScoreSeen` should decay over time instead of only ever increasing within a session.
**A checksum-valid barcode can still be the wrong barcode - deterministic, one-candidate-only correction for a specific real failure.** Real-device testing turned up a new failure class: OCR read `022000004840` (12 digits) - not garbled, and it passed its own checksum fine, so it went straight to a real Open Food Facts lookup - but the actual product's real code is `0220000048400` (13 digits). OCR had simply dropped the true trailing check digit, and the resulting 12-digit truncation happened to *also* independently satisfy a valid checksum at that shorter length, purely by coincidence. Unlike the guard-bar extra-digit case, there's no length-based tell here (12 is already a valid GTIN length) - this class of error is fundamentally harder to catch. Deliberately **not** solved the way the guard-bar case was (trying all 10 possible digits and accepting whichever "looks" valid) since that would risk occasionally "correcting" an already-genuinely-right code into a wrong one with no warning - a real, asked-about tradeoff, not a default reflex. Instead: a GTIN's check digit is a deterministic function of the digits before it, so `computeGTINCheckDigit()`/`extendedGTINCandidate()` compute the *one* mathematically correct extension for a length one-short-of-valid (7→8, 11→12, 12→13) - no guessing. `lookupProduct()` only ever tries this as a second lookup after the original scanned code has already failed to resolve (never overrides a code that already worked), and only accepts the extended candidate if *that* code is also confirmed to be a real registered product via its own lookup - tagged `source: 'OpenFoodFacts-corrected'` rather than blended in as an indistinguishable clean scan. Verified the control flow via a mocked `fetch` (original code returns not-found, extended code returns a real product) rather than live network calls, since Open Food Facts' API showed real flakiness while testing this - the same confirmed-good 13-digit code returned success on some calls and a 404 on others within the same session, unrelated to any of this code. If OFF inconsistency comes up again, suspect their API's own reliability before the app's logic.
**OCR fallback breaks "offline-first" on first use, same tradeoff as voice entry.** The vendored Tesseract assets (~8MB: JS + wasm + trained-language data) are self-hosted on this repo's own GitHub Pages, not a third-party CDN, but they still have to be fetched over the network the first time OCR fallback actually runs (lazy-loaded, not part of initial page load). After that first fetch, ordinary browser caching should make it available offline — untested whether the R1's WebView actually caches this reliably.
**A note for whoever touches Tesseract worker paths next:** `importScripts` inside the worker requires an *absolute* URL — a path like `js/vendor/tesseract/worker.min.js` that works fine for a normal `<script src>` tag throws `SyntaxError: ... is invalid` inside the worker. Paths are resolved via `absoluteUrl()` (`new URL(path, window.location.href).href`) so it also still works correctly when deployed under the GitHub Pages subpath, not just at a site root — don't revert to bare relative paths here.

**Fractional quantities default to whole-number stepping, fractions are opt-in.** Scrolling normally steps by 1 (fast, matches the majority case — cans, boxes, bottles). Tapping the quantity number toggles a per-field mode that steps by 0.25 within [0, 1] instead (0, 1/4, 1/2, 3/4, 1), for bulk goods like flour where "how full is it" matters more than a count. This was a deliberate tradeoff over unifying the stepping into one scale — a single quarter-stepped scale would slow down the common case (0→6 cans would take 9 scroll clicks instead of 6). The tradeoff: you can't currently represent "1 and a quarter bags" — fraction mode tops out at 1 "full unit." Revisit if that turns out to matter in practice.

**Visual design pass: warmer palette, serif headings, real animations, "app" over "tech preview."** All CSS values are now driven by `:root` custom properties in `css/styles.css` (`--bg`, `--accent`, `--ink`, etc.) rather than scattered hex literals - change the palette from one place. Headings, the app title, item names, and quantity numbers use a system serif stack (`Georgia, 'Iowan Old Style', 'Palatino Linotype', 'Book Antiqua', serif` - no web font loaded, keeps offline-first intact) while body/UI chrome stays sans-serif for legibility at small sizes. The neon-green terminal look (thick `#4caf50` border, harsh flat borders everywhere) was replaced with a muted warm-sage accent, softer borders, and a subtle outer shadow. Added: a CSS spinner (`.status-center::before`, pure CSS keyframe, no JS) on every "Looking up… / Reading… / Analyzing…" screen; a view-change fade+slide (`@keyframes viewIn` on `.view.active`); a proper "Saved" toast (`#savedToast` / `flashSaved()`) replacing the old barely-visible header-dot pulse; subtle press-scale feedback on buttons and menu items.
**Real layout regression caught by the scroll-height check, not a screenshot, while doing this pass.** Adding a 4th recovery-menu button in an earlier change had already pushed `recoveryView`'s content past the 240×282 frame (confirmed via `scrollHeight > clientHeight`, per the `r1-creation` skill's testing methodology - a screenshot alone would not have shown this since `overflow-y: auto` just scrolls silently instead of visibly breaking). Fixed by shrinking `.item-photo` (46px → 32px), `.menu-item` vertical padding (12px → 9px), `.menu-list` gap (7px → 5px), and the outer `.view` padding/gap (9px/7px → 8px/6px) - re-verified all eleven views sit at exactly `scrollHeight === clientHeight` afterward. Also added `.scan-debug:empty { display: none; }` so the OCR/recovery debug line doesn't reserve blank space when there's nothing to show.
**Preview-tooling gotcha hit while verifying this pass:** the headless preview browser's tab doesn't reliably paint frames (`requestAnimationFrame` never fired, confirmed by a callback that hung 30s+) and `preview_screenshot` timed out repeatedly and consistently, even across a fresh server restart - so CSS transitions/toasts can't be visually confirmed through this tool in this environment. Computed-style inspection (`getComputedStyle` via `preview_eval`, or the `preview_inspect` tool) and the CSSOM rule list still work fine and are what verified the toast/spinner CSS is actually correct - don't waste time re-trying `preview_screenshot` if it's already failed once in a session, and don't mistake a stuck `requestAnimationFrame` for a real bug in the app's CSS.

## Cross-platform support (runs outside the R1 too)

Same `index.html`/`css/styles.css`/`js/app.js` run unmodified on any modern browser (phone or desktop) - no separate build, no fork. This turned out to be less work than it sounds, because several things were already portable before this was ever asked for: `storageGet()`/`storageSet()` already fall back to `localStorage` when `window.creationStorage` doesn't exist; the camera already uses standard `getUserMedia` with a `<input type="file" capture="environment">` fallback; almost every screen already responds to a direct tap/click on its own buttons/items (`el.addEventListener('click', ...)`), independent of the R1's scroll-wheel-plus-PTT selection model - so basic navigation and confirming already worked cross-platform with zero changes.

**Fixed 240×282 layout now scales to fit any window, via a JS transform rather than a CSS rewrite - literally the same CSS renders everywhere.** The viewport meta changed from a hardcoded `width=240` (which forced every browser, including a phone, to treat the page as if it were exactly 240 CSS px wide) to standard `width=device-width`. `#app` itself is untouched - still a fixed `240x282` box with the exact same rules - but `html`/`body` now fill 100% of the real viewport and flex-center that box, and `fitStage()` in `js/app.js` applies `transform: scale(...)` computed from `Math.min(window.innerWidth/240, window.innerHeight/282)` (capped at 3x so it doesn't blow up absurdly large on a big desktop monitor), re-run on `resize`/`orientationchange`/`load` plus a defensive one-off retry shortly after load. On the R1 itself the viewport already is ~240x282, so this computes a scale of ~1 and changes nothing visually - verified in preview at a phone-sized viewport (375×812 → scale 1.5625, both axes centered correctly) and a desktop-sized one (1280×800 → height-constrained scale ~2.84, centered).
**One real interaction gap: "hold to cancel/back" has no non-R1 equivalent, so it's polyfilled generically rather than reworked per-screen.** Every other R1 gesture (`sideClick`, scroll-wheel index movement) turned out to be fully redundant with direct taps already wired up - confirmed by auditing every `sideClick`/`scrollUp`/`scrollDown` branch against existing per-element click listeners before writing anything. `longPressStart` (hold-to-go-back/cancel, and hold-to-delete on an existing item's card) had no such redundancy. Rather than add explicit "Back" buttons to every screen (more visual surface, and the user was explicit about being done tweaking the look), a press-and-hold (~500ms) anywhere on `#app` dispatches the *exact same* synthetic `longPressStart` window event the R1 fires - every existing per-view branch (including the delete-on-hold-for-an-existing-item behavior) runs completely unchanged on any device, since the dispatched event is indistinguishable from the real one. Verified in preview via the real navigation flow (not just toggling a `.active` class, which doesn't update the closured `currentView` variable and produces a false negative): entered Browse for real, dispatched a synthetic hold, confirmed it navigated back to Home exactly like a real R1 PTT hold would.
**Added on-screen tap targets for what the scroll wheel used to be the only way to do: quantity +/- (item card, manual entry, item detail).** These three screens' quantity steppers had no click/tap equivalent at all (unlike the fraction-mode toggle on the number itself, which already had one) - small `.qty-btn` buttons were added flanking each quantity display, wired to the same `adjustItemQty()`/`adjustManualQty()`/`adjustDetailQty()` functions the scroll wheel already called, so there's exactly one source of truth for quantity math regardless of input method. The detail view's buttons are injected via its existing dynamic HTML template (`renderDetail()`) rather than static markup, since that row's content is rebuilt on every render; its shared click-delegation handler (`detailRows.addEventListener('click', ...)`) checks for the new buttons *before* falling through to the existing fraction-toggle check, since the buttons are nested inside `#detailQtyRow` and would otherwise also trigger that.

## Known bugs already found and fixed (for context, don't re-introduce)

- **Camera-ready race condition** (fixed in `cb6f4f9`, then made moot by the tap-to-capture rewrite): starting an async operation's continuation only from the triggering navigation event, not from whichever happens later (navigation vs. the async operation itself completing).
- **Recovery view 3px overflow** on the 240×282 frame: caught via `scrollHeight > clientHeight` checks in preview, not visible in a screenshot that happened to just barely fit. Every view still has `overflow-y: auto` as a safety net regardless — see the `r1-creation` skill's testing methodology for why bare pass/fail isn't enough margin.
- **Barcode capture downsampled to a fixed 160×120 canvas** (fixed in `b4bcb0f`): destroyed the fine bar spacing barcodes need to decode, regardless of distance or focus — would only ever work by luck. Capture now uses the camera's native resolution (`videoWidth`/`videoHeight`); a 160×120 thumbnail is still generated afterward, but only for the stored item photo, from the already-captured full-res frame.
- **GitHub Pages build got stuck in `"building"` for this repo** during real-hardware debugging — real content deployed correctly per `git push`, but the Pages build never advanced, so the live site kept serving stale code well after fixes had been pushed and looked like device-side caching at first. See the `r1-creation` skill's `deployment-pipeline.md` (stuck-build gotcha) — always verify the live URL actually changed before trusting a "fixed" report from real-hardware testing.
- **Tap-to-toggle-fraction on the quantity display had a tiny, easy-to-miss tap target on a real finger** (item card + manual entry; the detail view was unaffected since it already delegates the click to the whole `#detailQtyRow`, not just the number). The click listener was bound to `.qty-value` itself, an `inline-block` sized exactly to its text glyph (e.g. `"1"`) — fine with a mouse pointer, much too small to reliably hit with a thumb, especially once flanked by the new `.qty-btn` +/- buttons. Fixed by moving the listener to the whole `.qty-stepper` wrapper (`#qtyStepper` / `#manualQtyStepper`) and giving that wrapper real padding (`8px 0`) so the clickable area matches its visible box, not just its text.

## R1 camera hardware facts (confirmed on real device)

- **Fixed-focus lens, sharp only from roughly 1–2 feet away.** Confirmed by holding a real barcode at varying distances while watching the live preview: it never sharpens at typical close scanning range (a few inches), only once backed off to about a foot or more. The scan hint text was updated to say this explicitly (`"Hold ~1-2ft back, click PTT"`) — don't revert that copy to anything implying close-range scanning without re-confirming this.
- `focusMode: 'continuous'` is requested as a best-effort `advanced` getUserMedia constraint — unverified whether the R1's camera actually honors it; harmless no-op if unsupported. A `zoom: 2` constraint was also tried (added back when bar decoding was still the plan, on the theory that more magnification meant more pixels per bar), but removed after real-device testing on small print (a gum box) got noticeably worse with it than without: `zoom` most likely crops the sensor's field of view rather than upscaling, which risks cutting part of a *small* barcode's digit line out of frame entirely - for OCR, a complete but smaller digit line is far more useful than a partial but larger one, since the whole line is needed to reconstruct a valid checksum.
- A settle delay (~300ms) plus a 3-frame decode burst was added to rule out button-press motion blur as a contributing factor — this shipped before the focus-distance finding, so its own marginal benefit (versus the distance fix alone) is unconfirmed.

## What's unverified on real hardware

This was all built and tested in a browser preview (see the `r1-creation` skill for why: no camera/mic in a headless preview browser). Specifically unconfirmed on the actual R1:
1. ~~Barcode (bar) capture reliability~~ — moot: bar decoding never worked on real hardware even after fixing resolution/capture/focus-distance, and was removed entirely (see "OCR-only scanning" above). Scanning is now OCR-only.
2. **OCR accuracy on small print** — confirmed working end-to-end on real hardware for a flat-labeled item (Zeiss lens wipes, `662834503500`), including recovering the correct value from a real, imperfect camera capture and correctly ignoring an unrelated printed code elsewhere on the package. Failed on a photographed-and-confirmed-real barcode (a 14-piece gum box, UPC-A `022000004840`) — OCR read `119 5 22 484 4 2`, catching fragments of the real digits (`22`, `484`) but garbling the rest. Small packaging like gum has a noticeably smaller printed barcode than something like the lens wipes box, and at the mandatory ~1-2ft scan distance that print becomes quite tiny in the captured frame - the leading theory, not yet confirmed. In response, removed an unnecessary downscale that was throwing away resolution for no real benefit: `OCR_MAX_DIMENSION` was capping every capture at 900px on the assumption `recognize()` needed that to stay fast, but real-device testing (`runDiagOcrRecognizeTest` in Diagnostics) showed `recognize()` only takes ~4s even at the camera's full ~2MP resolution - so it's now just a 2000px safety ceiling, not an active downscale. Removing the downscale alone still garbled the gum's digit line (though with visibly fewer wrong digits: `2 5 4 9 8`, versus `119 5 22 484 4 2` before) - looked more like OCR was only seeing *part* of the barcode than misreading the whole thing, which prompted also removing the `zoom: 2` constraint (see above). That combination still didn't fix it - the user directly diagnosed the real cause: the camera was picking up both the nutrition facts panel and the actual barcode at once, and Tesseract's own line-grouping was merging both into one recognized line. Fixed via `clusterWordsIntoRows()` (see "Extraction is scoped..." above) - verified against a synthetic reproduction of the exact layout, and the real barcode confirmed to actually exist in Open Food Facts (Orbit Spearmint Gum). Still needs a fresh real-device retest on the actual gum box to confirm this holds up outside the synthetic reproduction. The Deer Park water bottle failure mentioned in earlier notes was never root-caused (no debug text was captured that time) and remains open too - if it recurs, capture the recovery screen's debug line before changing anything.
   A curved/cylindrical label (a water bottle) warping the digit line is a separate, still-untested hypothesis from the small-print-size one above - don't conflate the two if both come up again.
3. **Voice entry accuracy** — does the Web Speech API even produce a `SpeechRecognition` instance in the R1's WebView, and if so, how accurate is it?
4. ~~Whether `getUserMedia` camera access continues to work reliably~~ — confirmed working: real-device testing got a live 1080×1920 stream.

## Original spec (condensed)

Core design principles: offline-first whenever possible; barcode scanning is the preferred input; AI only when necessary; every interaction operable with one hand; minimize typing; local storage works with no account; optional cloud sync later. Primary hardware: camera, scroll wheel, side button, microphone, speaker.

**Phase 1** (done): barcode scanner, local inventory, quantity management, Pantry location.
**Phase 2** (partially pulled forward — Vision AI and voice are done, with caveats above; OCR and expiration are not): OCR fallback from package photos, Vision AI fallback, voice entry, expiration tracking with "expiring today / this week / this month" notifications.
**Phase 3** (not started): shopping list (auto-generated from items flagged low/out-of-stock/frequently-purchased), recipes ("what can I cook?" using inventory + LLM, highlighting missing ingredients), statistics (most used, most wasted, average pantry value, monthly waste), multi-location inventory with a UI to create/switch custom locations beyond the default Pantry (Fridge, Freezer, Garage, Medicine Cabinet, Cleaning Supplies, Storage, Workshop, or user-defined).
**Phase 4** (not started): household sync, shared inventories, cloud backup, optional integrations.

Long-term vision: evolve from a pantry tracker into a full home inventory manager — one system for food, medicine, household supplies, tools, and storage bins, all using the same fast scan-first workflow.
